# USF Improvement Proposal: Enhanced AFP Gates for LibTIFF-Class False Positives

> **Proposal ID**: IMP-SEC-20251214-001
> **Category**: VERIFICATION (HIGH risk)
> **Source Agent**: MAL-ADVERSARIAL (post-mortem analysis)
> **Status**: PROPOSED
> **Date**: 2025-12-14

---

## 1. Executive Summary

The LibTIFF Apple Security Bounty analysis produced **4 false positive claims** (100% failure rate) despite using USF PL5 TMPL-SEC-AUTONOMOUS. This proposal adds 5 new AFP gates to prevent similar failures.

---

## 2. Root Cause Analysis

### 2.1 Failure Mode Classification

| Finding | Failure Mode | Why AFP Gates Failed |
|---------|--------------|---------------------|
| OJPEG | **Dual-Condition Protection Missed** | Didn't trace `subsamplingcorrect` guard on writes |
| WebP | **Platform Attack Surface Unverified** | Assumed Apple ships all LibTIFF codecs |
| LERC | **Protective Math Misanalyzed** | Truncation makes checks MORE restrictive |
| LZW | **State Machine Not Traced** | Claimed wrong line numbers |

### 2.2 Pattern Extraction

```yaml
failure_patterns:
  FP-PATTERN-1:
    name: "Dual-Condition Guard"
    description: "Vulnerability requires condition A, but writes only happen when condition B"
    example: "OJPEG: n can be 21845 when subsamplingcorrect!=0, but writes need subsamplingcorrect==0"
    detection: "Trace ALL conditions on write path, not just value derivation"

  FP-PATTERN-2:
    name: "Platform Attack Surface Assumption"
    description: "Vulnerable code exists but target doesn't ship/enable it"
    example: "WebP-in-TIFF exists in LibTIFF, Apple ImageIO doesn't support compression 50001"
    detection: "MUST verify platform actually enables vulnerable code path"

  FP-PATTERN-3:
    name: "Protective Arithmetic Inversion"
    description: "Truncation/overflow makes subsequent checks MORE restrictive, not less"
    example: "LERC: new_size truncation makes new_alloc check fail earlier"
    detection: "Trace BOTH truncated and original values through all checks"

  FP-PATTERN-4:
    name: "State Machine Location Error"
    description: "Claimed vulnerable lines are actually protected; real vuln is elsewhere"
    example: "LZW: Lines 509-521 have check at 507, real pattern is 544-559"
    detection: "MUST trace full state machine, verify check BEFORE write"

  FP-PATTERN-5:
    name: "Validation Bypass Assumption"
    description: "Assumed validation can be bypassed without proving bypass path"
    example: "OJPEG: Assumed n validation could be bypassed, but all write paths validate"
    detection: "Prove WHICH code path bypasses validation, not just that bypass is theoretical"
```

## 3. Proposed Changes

### 3.1 New AFP Gates (Add to Phase 3.5)

```yaml
afp_gates_v2:
  # EXISTING GATES (Retain)
  - gate: AFP-GATE-1  # Changelog Verification (existing)
  - gate: AFP-GATE-2  # Default Configuration (existing)
  - gate: AFP-GATE-3  # Source Code Verification (existing)
  - gate: AFP-GATE-4  # Working PoC Gate (in Phase 4, existing)

  # NEW GATES
  - gate: AFP-GATE-5
    name: "Control Flow Protection Analysis"
    version: "1.0.0"
    origin: "LibTIFF OJPEG false positive (2025-12-14)"
    description: |
      MANDATORY: Trace ALL conditions that guard vulnerable writes.
      Many vulnerabilities appear exploitable when analyzing value derivation
      but are protected by guard conditions on the WRITE operation itself.
    required_for: [HIGH, CRITICAL]
    methodology:
      step_1: "Identify ALL write operations that cause the vulnerability"
      step_2: "For EACH write, list ALL conditions that must be true"
      step_3: "For EACH condition, determine if attacker controls it"
      step_4: "If ANY write is protected by condition attacker can't control → BLOCK"
    checks:
      - "List every write operation in vulnerable function"
      - "Trace conditions: if/else, switch, ternary guarding each write"
      - "Determine if validation happens on SAME condition path as write"
      - "Check for dual-condition patterns (value derived in path A, write in path B)"
    example_check: |
      OJPEG:
      - Write: sp->sof_c[q] = o (line 1893)
      - Condition: if (sp->subsamplingcorrect == 0) (line 1892)
      - Value n derivation: when subsamplingcorrect can be !=0
      - Value n validation: when subsamplingcorrect == 0 (line 1822)
      - RESULT: Write and validation on SAME path → PROTECTED
    fail_action: "BLOCK finding, error AFP-3005"
    error_code: "AFP-3005"

  - gate: AFP-GATE-6
    name: "Platform Attack Surface Verification"
    version: "1.0.0"
    origin: "LibTIFF WebP/LERC false positive (2025-12-14)"
    description: |
      MANDATORY: Verify target platform ACTUALLY ships vulnerable code path.
      Library may contain vulnerable code that target doesn't compile/enable.
    required_for: [HIGH, CRITICAL, MEDIUM]
    methodology:
      step_1: "Identify compile-time/runtime guards on vulnerable code"
      step_2: "Determine target's build configuration"
      step_3: "Verify target enables vulnerable feature"
      step_4: "If target doesn't ship feature → REJECT with zero attack surface"
    checks:
      - "Check #ifdef guards on vulnerable code"
      - "Check compression/codec/feature tables in target"
      - "Verify target documentation lists feature as supported"
      - "Test if target actually processes vulnerable input format"
    example_check: |
      WebP-in-TIFF:
      - Code: tif_webp.c is #ifdef WEBP_SUPPORT
      - Apple ImageIO: Does NOT list WebP TIFF compression
      - TIFF compression 50001: "Unsupported" in ImageIO
      - RESULT: Attack surface = ZERO on Apple
    fail_action: "REJECT finding, error AFP-3006"
    error_code: "AFP-3006"

  - gate: AFP-GATE-7
    name: "Protective Arithmetic Trace"
    version: "1.0.0"
    origin: "LibTIFF LERC false positive (2025-12-14)"
    description: |
      MANDATORY: Trace BOTH original and truncated/overflowed values
      through ALL subsequent operations. Truncation may make checks
      MORE restrictive, not less.
    required_for: [HIGH, CRITICAL]
    methodology:
      step_1: "Identify the arithmetic operation (truncation, overflow)"
      step_2: "Trace ORIGINAL value through all subsequent uses"
      step_3: "Trace MODIFIED value through all subsequent uses"
      step_4: "Compare which value is used in protective checks"
      step_5: "If modified value makes checks MORE restrictive → REJECT"
    checks:
      - "What is the original calculation?"
      - "What is the modified (truncated/overflowed) value?"
      - "What checks use the original value?"
      - "What checks use the modified value?"
      - "Does the modification make any check fail EARLIER?"
    example_check: |
      LERC:
      - Original: new_size_64 (uint64_t)
      - Truncated: new_size (uint32_t)
      - Check: new_alloc != new_alloc_64 (uses new_alloc_64 which includes new_size_64)
      - new_alloc_64 = 1.33 * new_size_64
      - If new_size_64 > UINT32_MAX, new_alloc_64 > UINT32_MAX
      - Check catches overflow BEFORE allocation
      - RESULT: Truncation is protective, not vulnerable
    fail_action: "REJECT finding, error AFP-3007"
    error_code: "AFP-3007"

  - gate: AFP-GATE-8
    name: "State Machine Trace Verification"
    version: "1.0.0"
    origin: "LibTIFF LZW false positive (2025-12-14)"
    description: |
      MANDATORY: For complex code with state machines (parsers, codecs),
      trace FULL state machine to verify claimed vulnerable lines.
      Goto/switch/loop patterns can make control flow non-obvious.
    required_for: [HIGH, CRITICAL]
    methodology:
      step_1: "Identify state machine structure (labels, goto, switch)"
      step_2: "Trace EVERY path that reaches claimed vulnerable line"
      step_3: "For EACH path, verify no protective check precedes write"
      step_4: "Verify claimed line numbers against actual control flow"
    checks:
      - "Map all labels, goto targets, switch cases"
      - "Build control flow graph for vulnerable function"
      - "Trace each path to claimed vulnerable write"
      - "Verify check-before-write ordering on each path"
    example_check: |
      LZW:
      - Claimed: Lines 509-521 vulnerable
      - Actual: Line 507 has `if (codep > free_entp) goto error_code` BEFORE line 509
      - All paths to 509 must pass through 507
      - RESULT: Original claim WRONG - line 507 protects 509
    fail_action: "BLOCK finding, error AFP-3008"
    error_code: "AFP-3008"

  - gate: AFP-GATE-9
    name: "Validation Bypass Proof"
    version: "1.0.0"
    origin: "LibTIFF OJPEG false positive (2025-12-14)"
    description: |
      MANDATORY: If claiming validation can be bypassed, PROVE the
      bypass path with specific code flow. "Maybe bypassed" is not enough.
    required_for: [HIGH, CRITICAL]
    methodology:
      step_1: "Identify the validation being bypassed"
      step_2: "Trace ALL code paths that reach vulnerable operation"
      step_3: "For EACH path, verify validation is actually skipped"
      step_4: "Prove attacker can control which path is taken"
    checks:
      - "What validation is claimed to be bypassable?"
      - "What specific code path bypasses it?"
      - "What input triggers the bypass path?"
      - "Does the bypass path still reach the vulnerable write?"
    example_check: |
      OJPEG:
      - Validation: n != samples_per_pixel check (line 1822)
      - Bypass claim: "subsamplingcorrect != 0 skips validation"
      - Bypass path: TRUE, validation skipped when subsamplingcorrect != 0
      - BUT: Writes at 1893, 1919, 1948 require subsamplingcorrect == 0
      - RESULT: Bypass path doesn't reach vulnerable writes
    fail_action: "BLOCK finding, error AFP-3009"
    error_code: "AFP-3009"
```

## 4. Expected Impact

### 4.1 Benefits

| Metric | Before | After | Delta |
|--------|--------|-------|-------|
| False positive rate | ~50-100% | <10% | -90% |
| Credibility damage incidents | High | Low | Significant |
| Bounty rejection rate | High | Low | Significant |
| Time spent on rejected findings | High | Low | -80% |

### 4.2 Costs

| Resource | Impact |
|----------|--------|
| Analysis time | +50% per finding (offset by fewer false submissions) |
| Gate complexity | 5 new gates to implement and maintain |
| Context requirements | Need full source access for all gates |

### 4.3 Trade-offs

- **More rigorous = slower**: Each finding requires deeper analysis
- **Some real vulns might be blocked**: Conservative gates may require human override
- **Mitigation**: Add "AFP-OVERRIDE" command for human to bypass gates with documentation
